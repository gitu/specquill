# Multi-stage source authorization

Reference sources (regulation texts, other repos, code) power AI grounding —
but the in-repo config is writable by anyone with push access, so what it
says must never mint access. Two authorization chains satisfy that
invariant, one per auth mode ([references.md](../specs/references.md)).

**Local-auth mode** — the server holds shared credentials, so definitions
stay server-side:

> **REQ-004.1 · MUST** — Credentials and remote URLs SHALL only be defined in
> the app catalog (stage 1); credentials come from the environment, never
> from the database or any in-repo file.

> **REQ-004.2 · MUST** — Tenant administrators SHALL grant catalog sources to
> the tenant (stage 2) before any project can use them.

> **REQ-004.3 · MUST** — The in-repo project config SHALL only select granted
> sources by name (stage 3); ungranted selections are surfaced as warnings
> and never fetched.

**Forge-PAT mode** ([REQ-024](REQ-024.md)) — the server holds no
credentials, so the in-repo config may *define* sources without being able
to grant anything:

> **REQ-004.5 · MUST** — In-repo source definitions SHALL be materialized
> exclusively with the requesting user's own token into that user's
> isolated storage — the forge's permission check is the authorization, and
> a source one user fetched is never served to another.

> **REQ-004.6 · MUST** — In-repo source remotes SHALL be http(s) URLs;
> filesystem paths are rejected so repo content cannot read local
> repositories on the server.

**Both modes**:

> **REQ-004.4 · MUST** — Write operations SHALL require at least the
> editor role on the repository ([REQ-021](REQ-021.md)); tenant
> administration requires the tenant admin role (stage 4).
