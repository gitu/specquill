# Token-scoped dynamic projects with clone quota and idle cleanup

In forge-PAT deployments ([REQ-024](REQ-024.md)) that opt in, the configured
project list stops being the boundary of what can be edited: an
authenticated user may open **any workspace-hosting repository their own
token can reach** — one that declares its workspaces in a root
`.specquill/config.yml` manifest — as additional projects, with no
per-repository server configuration. The configured main project
remains the login and role anchor — dynamic projects extend what an editor
can reach, they never change who gets in or what role they hold.

> **REQ-025.1 · MUST** — Dynamic projects are **opt-in per deployment**:
> disabled by default, enabled explicitly in the server configuration — a
> deployment that does not opt in behaves exactly like v1, its configured
> projects the entire editable surface. When enabled, a user SHALL be able
> to open workspaces from a repository — named as `owner/repo[.git][#name]`,
> a full remote URL, or a pick from search — that satisfies BOTH gates:
> it lives on the deployment's configured forge host and it alone
> (`github.com` for a github.com deployment, the self-hosted GitLab host
> for one of those — never arbitrary hosts: the token belongs to that host
> and is never offered elsewhere, and the server must not become an
> anonymous mirror of arbitrary public remotes), and it **declares itself a
> workspace host** with a root `.specquill/config.yml` on its default
> branch — a repository without one is not openable, however far the token
> reaches. That manifest decides what is openable: without a `projects:`
> list the repository root is its single workspace and `owner/repo` opens
> it; with one, each entry — a stable **name** plus a workspace **root**
> ([REQ-003](REQ-003.md)) — is an openable subproject addressed as
> `owner/repo#name`, and opening the bare repository offers the declared
> list. A declared root whose folder does not exist yet is valid: the
> declaration is the consent, and the first proposed change creates the
> folder.

> **REQ-025.2 · MUST** — Repository search is a **separate opt-in on top**
> of REQ-025.1: a deployment may allow opening by explicit name or URL
> without offering search. When enabled, search SHALL be delegated to the
> forge with the requesting user's own token, so the searchable corpus is
> exactly what that token can reach. The switch is server-exposure control,
> not secrecy — a token holder can always enumerate their repositories
> against the forge directly; what the deployment decides here is whether
> its OWN server proxies forge search traffic (egress, rate limits, audit
> posture).

> **REQ-025.3 · MUST** — Opening SHALL follow the per-user isolation of
> REQ-024.4: materialization runs with the requesting user's token into that
> user's own storage; a repository the token cannot fetch yields an error
> and leaves nothing on disk. What the user may DO in a dynamic project is
> bounded by their forge permission on that repository, and by it alone —
> the anchor-derived deployment role ([REQ-024](REQ-024.md)) gates login
> but neither grants nor caps capability here: read-only access yields a
> read-only project (surfaced as such on open, not as a failure at propose
> time), and a deployment-role viewer who maintains a repository edits it.
> Every dynamic project materializes as its own clone, even when several of
> a user's projects sit in one repository under nested content roots — full
> isolation (own branches, own drafts) is chosen over shared state, and
> each clone pays into the byte budget separately. Dynamically opened
> projects are per-user state — one user's open list is neither visible to
> nor openable by proxy for anyone else.

> **REQ-025.4 · MUST** — Every dynamic project SHALL have a stable identity
> derived from (the forge's stable repository id, the declared subproject
> name) — from neither spellings nor paths: `owner/repo#name` is resolved
> through the forge API at open, so a renamed repository converges on the
> same project instead of silently splitting workspace branches and drafts
> across an old and a new identity, and the manifest maps the name to its
> root, so even a workspace folder that moves within the repository keeps
> its identity. URLs, branches and drafts survive close, cleanup,
> re-materialization and both kinds of rename, and the same spelling opens
> the same project for every user — each through their own token. Unauthenticated share bundles ([REQ-016](REQ-016.md)) are NOT
> available on dynamic projects: a shared URL resolves only for
> authenticated users, and what a recipient sees materializes through the
> recipient's own token — the forge gates every read, including shared ones.

> **REQ-025.5 · MUST** — Per-user server-side storage SHALL be bounded by a
> deployment-configurable **byte budget** covering everything materialized
> for that user — dynamic projects and the reference clones they pull in
> alike (a project count would miss both monorepos and the sources an opened
> repository's own config drags along). Opening beyond the budget SHALL be
> refused with an error naming the budget and pointing at the overview
> (REQ-025.9). A user SHALL be able to close any of their dynamic projects
> at any time to free space — closing one whose clone holds unsynced state
> (as defined in REQ-025.6) requires explicit confirmation that the work is
> discarded.

> **REQ-025.6 · MUST** — A clone unused for a deployment-configurable idle
> period SHALL be reclaimed automatically; **any authenticated request that
> touches the repository counts as use**, so reclamation targets genuinely
> abandoned checkouts, not momentarily quiet ones. A clone holding state
> that exists nowhere else — a dirty worktree of uncommitted draft edits
> (commits are on the forge already, REQ-025.10) — is exempt, but only up
> to a deployment-configurable **retention cap** well beyond the idle
> period: past it the clone is reclaimed even though that discards the
> unsynced edits. That loss is deliberate and this requirement says so —
> an operator's storage promise has to end somewhere. Reclamation frees
> budget and disk only; the project entry survives, and reopening
> re-materializes the clone on demand.

> **REQ-025.7 · SHOULD** — Idle reclamation SHOULD extend to every per-user
> clone (the anchor project and in-repo reference sources included), under
> the same never-while-dirty rule — a user who stops logging in eventually
> costs no disk.

> **REQ-025.8 · MUST** — Read-only reference repositories (grounding
> sources) SHALL be materialized as shallow clones: only the tip of the
> default branch is needed for browsing and speccy grounding, full history
> stays on the forge. A feature that genuinely needs history on a reference
> may deepen on demand; writable project clones are exempt — workspace
> branches, merges and history views need real history.

> **REQ-025.9 · MUST** — The user SHALL have an overview of every
> repository materialized for them — dynamic projects, the anchor clone and
> reference clones — showing for each at least when it was last used and
> whether it holds unsynced state (a dirty worktree), with per-entry
> cleanup: reclaim clean clones immediately, unsynced ones only with the
> explicit discard confirmation of REQ-025.5.

> **REQ-025.10 · MUST** — A commit on a workspace branch SHALL be pushed to
> the forge immediately, with the committing user's own token, so committed
> work never exists only in a server-side clone. The unsynced state
> REQ-025.6 protects thereby shrinks to uncommitted worktree edits — every
> commit survives any reclamation because the forge already holds it.
