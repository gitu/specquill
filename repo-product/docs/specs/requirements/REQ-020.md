# Per-repository user grants

Beyond the deployment role, an administrator SHALL be able to grant a user
an explicit role on a single repository — an external reviewer scoped to
one repo, a user without any git-host account, or a user whose deployment
role is lower than their intended role on that repo. The server pushes with
its own credentials, so the application layer is the effective gate.

> **REQ-020.1 · MUST** — An admin SHALL grant `viewer` or `member` on one
> repository to a user identified by email. Grants compose with the
> deployment role by maximum; they SHALL never be created, changed or
> revoked by enrollment or configuration syncs.

> **REQ-020.2 · MUST** — Roles SHALL be enforced per repository on every
> request: below `viewer` nothing is reachable, `viewer` reads and comments,
> mutations (writes, commits, PR create/approve/merge/close, co-editing,
> copilot drafts) require `member`. A viewer SHALL NOT be able to write
> through any route.

> **REQ-020.3 · MUST** — A grant-only user SHALL see exactly the granted
> repositories — no deployment management, no other repos.

> **REQ-020.4 · MUST** — Granting an email with no account yet SHALL leave
> a pending invite (case-insensitive) that becomes a grant on the invitee's
> first login, whichever provider they use.

> **REQ-020.5 · SHOULD** — `auth.default_role` SHALL control what
> authenticated users get: `member` (default, self-host semantics),
> `viewer`, or `none` — with `none`, access comes from grants alone
> (restricted deployments); configured admin emails still bootstrap as
> admin.
